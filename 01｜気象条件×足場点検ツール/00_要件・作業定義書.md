## 3. 言語・技術の選定

### 3-1. 結論：**C#（ASP.NET Core）を推奨します**

| 観点 | C# (ASP.NET Core) | Java (Spring Boot) |
|---|---|---|
| SQL Server との相性 | **◎ 同じMicrosoft製。設定がほぼ不要** | ○ JDBCドライバの導入が必要 |
| Windows認証 | **◎ そのまま使える** | △ 追加設定が必要 |
| Windowsでの常時稼働 | **◎ Windowsサービス/IISで標準的** | ○ 可能だが手順が多い |
| 開発ツール | **◎ Visual Studio が無料で強力** | ○ IntelliJ等（有料版が主流） |
| 初心者の学びやすさ | **○ 日本語の情報が多い** | ○ 同程度 |
| 導入費用 | **無料** | 無料 |

**現在の環境（Windows・SQL Server・Windows認証）に対して、C# は「そのまま繋がる」選択です。** Java でも実現できますが、接続まわりの設定が増え、初心者が最初につまずきやすい部分が多くなります。

### 3-2. 画面の作り方

**ASP.NET Core MVC ＋ HTML/CSS** とします。

- **HTML** … 画面の骨組み
- **CSS** … 見た目（色・文字サイズ・配置）
- **C#** … データの取得と計算
- **JavaScript** … 地図と絞り込みの動き（最小限）

> **Blazor という選択肢もあります**が、C# だけで画面まで書ける代わりに、HTML/CSS の学習にはなりません。「HTML に CSS を設定したものに変換したい」というご要望から、MVC ＋ HTML/CSS を選んでいます。

### 3-2-2. JavaScript は素のまま使う（フレームワークを入れない）

地図やモーダルを扱うため、JavaScript の使い方を先に決めておきます。

**React や Vue のようなフレームワークは入れません。素の JavaScript だけで書きます。**

| 方法 | 判断 |
|---|---|
| **素のJavaScript** | **採用。** 学ぶことが増えず、社内共通CSSがそのまま使える |
| React / Vue | 採用しない。作りが大きく変わり、初心者には負担が大きい |
| jQuery | 採用しない。今の JavaScript には同じことが標準で入っている |

#### なぜ素のままで足りるのか

**社内共通CSS が、素の JavaScript で動かす前提で作られているためです。**

`modal.css` や `panel.css` は「**クラスを付け外しすれば表示が切り替わる**」構造になっています。JavaScript 側は1行で済みます。

```javascript
// モーダルを開く
document.getElementById('site-modal').classList.remove('hidden');

// 閉じる
document.getElementById('site-modal').classList.add('hidden');
```

フレームワークを入れると、この仕組みと二重になり、かえって複雑になります。

#### 役割の分け方

**画面の中身は C# 側で作り、JavaScript は「動き」だけを担当します。**

| 担当 | 内容 |
|---|---|
| **C#（サーバー側）** | データベースから読む、判定する、**HTMLを組み立てる** |
| **JavaScript（画面側）** | 地図を描く、モーダルを開閉する、表を絞り込む |

こうすると、**JavaScript が薄く保たれます。**表の中身や判定結果は C# が作るので、JavaScript でデータを組み立てる必要がありません。

#### 地図について

地図だけは JavaScript が主役になります。**Leaflet**（無料・軽量）を使い、次のように渡します。

```
C#が現場の一覧をJSONで埋め込む → JavaScriptがLeafletで地図に描く
```

Leaflet も1ファイル読み込むだけで、フレームワークではありません。

#### ファイルの置き方

```
wwwroot/js/
  map_地図.js          地図の表示と色分け
  modal_モーダル.js     モーダルの開閉
  filter_絞り込み.js    表の絞り込み
```

**CSSと同じく、役割ごとに分けて日本語の説明を付けます。**

### 3-3. 見た目の土台：社内共通CSSを使う

`StandardCSS/` に、既存の社内アプリから抜き出した**共通CSS一式**があります。**これをそのまま土台にします。**

自前で色や余白を決めずに済み、**社内の他アプリと見た目がそろいます。**

#### 収録内容

| ファイル | 役割 |
|---|---|
| `variables.css` | **すべての色・寸法の出どころ**（デザイントークン） |
| `base.css` | リセット・ツールチップ・ローディング |
| `button.css` | ボタン（`.active-btn` / `.passive-btn` / `.toggle-btn` / `.small-btn`） |
| `modal.css` | モーダル（`.modal` / `.modal-content` / `.form-group` / `.button-row`） |
| `panel.css` | 浮かせる小パネル（`.floating-panel` / `.segmented`） |
| `switch.css` | ON/OFF スイッチ |
| `header.css` | 上部メニューバー（`.top-menu` / `.top-filters`） |

#### 守る約束

`StandardCSS/README.md` に書かれている決まりに従います。

1. **直値の色を書かない。** `#4EA1D5` などは禁止。必ず `var(--color-primary)` を使う
2. **色の意味を守る。** 青＝操作可／グレー＝無効・中立／赤＝破壊的
3. **部品CSSに固有サイズを書かない。** 個別画面は配置と幅・高さだけ書く
4. **`variables.css` は触らない。** アプリ固有の色はアプリ側で `:root` に追記する

#### 読み込む順番（決まっています）

```html
<link rel="stylesheet" href="css/variables.css">
<link rel="stylesheet" href="css/base.css">
<link rel="stylesheet" href="css/button.css">
<link rel="stylesheet" href="css/modal.css">
<link rel="stylesheet" href="css/panel.css">   ← modal.css より後ろ
<link rel="stylesheet" href="css/switch.css">
<link rel="stylesheet" href="css/header.css">
<link rel="stylesheet" href="css/app.css">     ← このアプリ固有
```

`panel.css` は `modal.css` の指定を引き継ぐため、**順番を入れ替えると崩れます。**

#### このアプリで追加する色

共通CSSに無い色は、`app.css` 側で組み立てます（README の「アプリ固有の色を足すとき」に従います）。

| 用途 | 現在の値 | 扱い |
|---|---|---|
| **部署ごとの地図の色**（8色） | 検証済みの配色 | **そのまま使う**。色覚特性のある方でも区別できるよう検証した組み合わせのため、共通トークンに寄せると識別性が落ちる |
| アラートの状況（未対応／指示済） | 赤／橙 | **共通トークンに寄せる**（`--color-danger` / `--color-warning`）。意味が同じため |
| 警報級の可能性（高／中） | 赤／橙 | 同上 |

> **部署の色だけは例外扱いにします。** 見た目をそろえることより、**地図上で8部署を見分けられること**を優先します。理由を `app.css` にコメントで残します。

#### 注意点（README より）

Visual Studio の「ドキュメントのフォーマット」を実行すると、`.floating-panel` が
`.floating - panel` のように**ハイフンの前後に空白が入り、CSSが全滅する**ことがあります。
整形設定を確認したうえで作業します。

### 3-4. 文字サイズについて（要確認）

共通CSSの基準は次のとおりです。

| トークン | 値 |
|---|---|
| `--font-size-base` | **14px** |
| `--font-size-lg` | 16px |
| `--font-size-title` | 20px |

一方、現在の Streamlit 版は「**年配の管理者が読みづらい**」というご要望を受けて、本文を **11pt（約15px）** に設定しています。

**社内標準（14px）に合わせるか、読みやすさを優先して大きくするか**を決める必要があります。→ 第9章 9-5

### 3-5. 地図について

現在の地図（folium）は Python 専用です。**Leaflet** という無料の JavaScript ライブラリに置き換えます。

- 地理院タイルをそのまま使えます（**出典表示の義務も継続**）
- 現在と同じ「部署ごとの色分け」「クリックで詳細」ができます

### 3-6. フォントについて

共通CSSは `M PLUS 2`（本文）と `Montserrat`（見出し）を指定しています。どちらも Google Fonts の無料フォントです。

**インターネットから読み込む形になります。** 気象庁のデータを取りに行けている環境なので問題ない想定ですが、社内の制限で外部サイトへ繋げない場合は、フォントファイルを同梱する方法に切り替えます。

### 4-1. 分ける理由

| 分け方 | 理由 |
|---|---|
| **画面と中身を分ける** | 画面の見た目を直すときに、判定の処理を触らずに済む |
| **判定を1事象1ファイル** | 「強風の基準を変えたい」ときに、その1ファイルだけ見ればよい |
| **取得を1データ1ファイル** | 気象庁の配信形式が変わったとき、影響範囲が1ファイルに収まる |
| **設定を1か所に** | 移設先の共有PCは**名前が未定**。接続先を1か所にまとめておけば、決まったときに1行の書き換えで済む |

## 5. 移植する機能（現行と同じ動作にする）

### 5-1. 判定（法令の中核）

| 事象 | 基準 | 判定の範囲 | 重複の防ぎ方 |
|---|---|---|---|
| 大雨 | 12時間積算 **50mm** 以上 | 直近3時間の観測値 | 同じ現場・同じ事象で12時間以内は再発報しない |
| 強風 | 10分平均 **10m/s** 以上 | 直近24時間 | 同じ現場・同じ日で1件 |
| 暴風 | 瞬間 **30m/s** 以上 | 直近24時間 | 同じ現場・同じ日で1件 |
| 大雪 | 24時間降雪量 **25cm** 以上 | 直近24時間 | 同じ現場・同じ日で1件 |
| 地震 | **震度4** 以上 | 直近48時間 | 同じ現場・同じ地震で1件 |

**共通の条件**：削除されていない／足場がある／状態が稼働中または休止中

**紐付いた観測所のうち最大値を採用**します（見逃しを防ぐため）。

### 5-2. 画面

| 画面 | 主な内容 |
|---|---|
| ダッシュボード | アラート一覧・全現場の地図・現場別の最新観測値・直近の雨/風/地震・取得ボタン |
| 気象予測 | 区域の色分け地図・基準に達する予測・警報級の可能性・時間ごとの動き |
| 点検記録簿 | 悪天候⇔点検の対応表・CSV出力（**臨検で提示する資料**） |
| 操作の練習 | 説明用。**記録は残らない** |

### 5-3. 定期実行

気象取得 → 地震取得 → 予測取得 → 判定 の順に、1時間ごと。

| 対象 | 扱い |
|---|---|

## 7. 作業の進め方（段階）

**一度に全部は作りません。** 段階ごとに動く状態にし、現行と結果を突き合わせてから次へ進みます。

すべての段階を**会社支給の個人PC**で確認します。共有PCへ移すのは最後です。

| 段階 | 内容 | 完了の目安 |
|---|---|---|
| **第1段階** | 環境構築・DB接続確認 | 現場数が画面に出る |
| **第2段階** | 判定処理の移植 | **現行と同じアラートが出る**（下の検証） |
| **第3段階** | 気象データ取得の移植 | 取得件数が現行と一致 |
| **第4段階** | ダッシュボード | 地図・一覧・絞り込みが動く |
| **第5段階** | 気象予測画面 | 予測と地図が出る |
| **第6段階** | 点検記録簿・操作の練習 | CSV出力まで |
| **第7段階** | 現場登録（Excel取り込み）の移植 | 現行と同じ件数が登録できる |
| **第8段階** | 24時間稼働PCへ移設 | 常時稼働・自動実行 |

### 7-1. 検証の方法（第2段階が最重要）

**同じデータベースに対して、Python版と C#版の両方で判定を実行し、結果が一致することを確認します。**

```
Python版の判定結果  ←→  C#版の判定結果
   件数・現場・事象・発生日時・観測値がすべて一致すること
```

**一致しない場合は先へ進みません。** 法令判定を間違えると、点検義務の見逃しにつながります。

### 7-2. 並行稼働

**移行が終わるまで Python版は止めません。** C#版が正しく動くと確認できてから切り替えます。

## 8. リスクと注意点

| リスク | 内容 | 対策 |
|---|---|---|
| **判定の作り込み違い** | 5,000行の中には、不具合対応で積み上げた細かい判断が多数ある（例：風速CSVの列名が日付で変わる、雪は正時のみ配信、同じ日に何度も発報しない仕組み） | 段階ごとに現行と突き合わせる。判定は最初に移す |
| **保守できる人が限られる** | 現在は Python 1種類。移行後は C# と Python の2種類になる | 現場登録以外は C# に寄せる。コメントを厚くする |
| **作業量** | 現行 約5,000行の作り直し。**数か月規模** | 段階を切り、途中でも使える状態を保つ |
| **同時アクセス** | 複数人が同時に使う想定になる | ASP.NET Core は標準で対応。接続の扱いに注意 |

### 8-1. 正直な見解

**今の Python版は動いており、試用も始まっています。** 作り直しは「動くものを作り直す」作業で、**新しい機能は1つも増えません。**

それでも移行する価値があるのは、次の場合です。

- 長期運用が決まっており、**保守しやすさが重要**
- **画面の作り込み**を今後増やしていきたい
- **C# を習得したい**という意図がある

逆に、**「24時間稼働させたい」だけが目的であれば、Python版のまま共有PCへ移すのが最短**です（半日程度）。移行と24時間稼働は、切り離して考えられます。

## 9. 決定事項

| 項目 | 決定 |
|---|---|
| **言語** | **C#（ASP.NET Core）** |
| **移行の範囲** | **全部**（画面・取得・判定すべて C#） |
| **24時間稼働の時期** | **作り直してから移設する** |
| **進め方** | **段階ごとに確認しながら進める** |

### 9-1. 作業する場所（PCの役割）

**3台のPCが関わります。役割が違うので、混同しないよう整理します。**

| PC | 役割 | SQL Server | 開発環境 |
|---|---|---|---|
| **私物のPC** | ファイルを作る場所。GitHub へ push する | **無し** | 無し |
| **会社支給の個人PC** | **実際に動かして確認する場所**。GitHub から pull する | **有り**（`24DECNMO001\SQLEXPRESS`） | **ここに入れる** |
| **共有PC（24時間稼働）** | 最終的な移設先。**名前は未定** | 移設時に用意 | 不要（動かすだけ） |

```
  私物のPC              GitHub            会社支給の個人PC
 （ファイル作成） ──push──→ ○ ──pull──→ （ビルド・動作確認）
                                                  │
                                                  │ 完成後
                                                  ▼
                                          共有PC（24時間稼働）
                                          ※名前は未定
```

**Visual Studio は「会社支給の個人PC」に入れてください。** SQL Server があり、実際に動かす場所だからです。

### 9-2. 接続先は設定ファイルにだけ書く

移設先の共有PCの**名前がまだ決まっていない**ため、サーバー名をプログラムの中に書きません。

**`appsettings.json` という設定ファイル1つ**に集約します。

```json
{
  "ConnectionStrings": {
    "ScaffoldAlert": "Server=24DECNMO001\\SQLEXPRESS;Database=PoC_ScaffoldAlert;..."
  }
}
```

移設のときは、**このファイルのサーバー名を書き換えるだけ**です。C# のコードは1行も触りません。

> 現在の Python 版は、`app.py` / `fetch_weather.py` など**8ファイルすべてにサーバー名が書かれています**。移設時に書き換え漏れが起きやすい状態です。C#版ではこれを1か所にまとめます。

### 9-3. 検証と移設の流れ

```
[第1段階]  手元のPC ＋ 手元のデータベースで作る・検証する
              ↓  すべて動くことを確認
[第2段階]  24時間稼働PCへ、スクリプトとデータベースを移設する
```

**まず手元で完成させてから移設します。** 移設先でいきなり作らないため、うまくいかない場合でも本番に影響しません。

### 9-4. ★重要な前提：テーブル名・項目名が変わる可能性がある

移設先では、**別の担当者が既に作成したテーブルを流用できる可能性**があります。その場合、**テーブル名や項目名が今と変わります**（特に現場リスト）。

これはアプリの作り方に大きく影響するため、次の対策を取ります。

#### 対策1：SQLを書く場所を1か所に閉じ込める

データベースを読み書きする文（SQL）は **`Data/` フォルダの中だけ**に書きます。画面や判定の処理には一切書きません。

名前が変わったとき、**直す場所が `Data/` に限られます。**

#### 対策2：★データベース側に「変換用のビュー」を作る

**これが本命の対策です。**

移設先のテーブルが違う名前・違う項目名でも、**アプリが期待する形に見せかけるビュー**を作れば、**C#のコードは1行も直さずに済みます。**

```
移設先の実際のテーブル              変換用のビュー          アプリ
┌────────────────────┐      ┌──────────────┐    ┌──────┐
│ 工事管理マスタ            │      │              │    │      │
│   工事コード              │ ──→  │  V_App_Site  │──→ │ C#   │
│   工事名                  │      │   SiteCode   │    │      │
│   所在地                  │      │   SiteName   │    │(無修正)│
└────────────────────┘      │   Address    │    └──────┘
                                    └──────────────┘
```

**ビューの中身だけを書き換えれば、名前の違いを吸収できます。**

そのため、アプリからは**必ずビューを経由**して読むように作ります。書き込み（アラート・点検記録）は自社で作ったテーブルなので、そのまま扱います。

#### 対策3：対応表を文書に残す

`20_データベース対応表.md` を作り、**「アプリが使う名前」と「実際のテーブル・項目名」の対応**を一覧にします。移設時にはこの表とビューだけを見れば済みます。

### 9-5. 決めていただきたいこと：文字サイズ

社内共通CSSの本文は **14px**、現在の Streamlit 版は **11pt（約15px）** です。

| 案 | 内容 |
|---|---|
| **A. 社内標準に合わせる（14px）** | 他アプリと統一される。現在よりわずかに小さい |
| **B. 読みやすさを優先して大きくする** | `app.css` で本文を 16px 程度に上書き。現場所長（50〜60代）が読みやすい |
| **C. 利用者が切り替えられるようにする** | 画面に「文字を大きく」を置く。作りは少し増える |

**推奨は B です。** この画面は「一目で状況を把握する」ことが目的で、読みやすさが業務に直結します。共通CSSは `app.css` での上書きを許しているため、約束を破ることにもなりません。

### 9-6. コンパイル確認について

ファイルを作るのは**私物のPC**、ビルドして動かすのは**会社支給の個人PC**です（9-1）。

私物のPC には **.NET SDK が入っていません**（実行環境のみ）。そのため、**私が書いたC#のコードは、私の側でコンパイル確認ができません。**

- コードは書けます
- **誤りがあれば、手元でビルドしたときに初めて分かります**
- ビルドのエラーが出たら、そのまま貼っていただければ直します

Python のときは私の側で構文確認ができていましたが、C#ではその確認が1段階減ります。**段階ごとに小さく作り、都度ビルドして確認**する進め方が重要になります。
