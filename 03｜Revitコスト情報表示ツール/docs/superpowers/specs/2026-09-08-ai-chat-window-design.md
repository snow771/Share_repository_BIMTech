# AIチャットウィンドウ — 設計

日付: 2026-09-08
対象: BUI Revit 2025アドイン（`BUI_Addin_CSharpアドイン`）

## 1. 何を作るか

設定タブにLLMの接続口はあるが、AIと会話する場所がない。
リボンに「AIに聞く」を置き、自然言語で建材を**検索・比較・提案**できる別ウィンドウを開く。

確認済みの決定事項。

| 論点 | 決定 |
| --- | --- |
| 権限の範囲 | **提案まで。**Revitへの反映は今までどおり手順1・手順2で人が行う |
| 画面の場所 | **別ウィンドウ。**BUIパネルは細長く、会話には狭い |
| 選択の参照 | **知っている。**選択中の1要素の情報をAIへ渡す |
| 検索の担い手 | **BUIが決定的に行う。**LLMは質問を絞り込み条件へ翻訳し、結果を説明するだけ |

## 2. なぜ「検索はBUIが行う」のか

LLMにクエリを書かせて実行する案は採らない。
顧客のDBに対してLLMが書いたSQLを流すことになり、CSV側には同じ仕組みが作れず、
失敗したときに利用者が原因を追えない。この案件が積み上げてきた
「検索は決定的、LLMは説明だけ」という方針を崩す。

全件をLLMへ渡す案も採らない。ローカルLLMに数千件は入らず、遅く、
質問のたびにマスタ全体を送ることになる。

**AIの答えと【検索】タブの絞り込み結果が食い違わないこと**が、
この機能を信用できるかどうかの分かれ目である。だから同じエンジンを通す。

## 3. 1往復の流れ

```
質問「この壁の仕上を不燃にしたい」
        ↓
  ①LLM  質問＋選択中の情報 → 絞り込み条件（JSON）
        {"selections":{"建材分類":"せっこうボード","厚さ":"12.5"},"text":"不燃"}
        ↓
  検証   各値を「その時点で実際に選べる値」と突き合わせる
        寄せられれば寄せ、無い値は落とす
        全部落ちたら質問文のキーワード検索に切り替える
        ↓
  BUI    ICandidateSource.QueryAsync ← 検索タブと同じエンジン
        候補 N件（20件まで）
        ↓
  ②LLM  候補＋質問 → 日本語の説明・比較・提案
        ↓
  照合   回答中のProduct_IDをマスタと突き合わせ、
        無いIDに「※このIDはデータにありません」と印を付ける
```

### 3.1 検証の材料

`CandidateView.Filters` が「いまその項目で選べる値」を返す。
LLMが `"厚さ":"12.5mm"` と書いても、実データの値が `12.5` なら**そちらへ寄せる**。
寄せられなければその条件だけ落とす。存在しない条件で0件になって終わることを防ぐ。

寄せ方は次の順で判定し、最初に一致したものを採る。

1. 完全一致
2. 前後の空白を除いた一致
3. 大文字小文字を無視した一致
4. 数字と小数点だけを取り出した一致（`12.5mm` と `12.5`）

どれにも当たらなければ、その項目は未選択（すべて）にする。

### 3.2 LLMがマスタ全体を見ることはない

②へ渡すのはBUIが選んだ20件までである。

## 4. 部品

| 置き場 | 部品 | 役割 |
| --- | --- | --- |
| `Bui.Shared` | `CandidateQueryPlanner` | ①の出力を検証して `CandidateQuery` にする。偽のLLMで単体テストできる |
| `Bui.Shared` | `LlmChatSession` | 会話の状態と1往復の手順。Revit非依存 |
| `Bui.Shared` | `ProductIdMentionChecker` | 回答中のIDをマスタと照合 |
| `Bui.Shared` | `BuiChatViewModel` | 画面の状態。送信、中断、検索タブへ送る、リセット |
| `Bui.Addin` | `BuiChatWindow`（WPF） | 別ウィンドウ本体 |
| `Bui.Addin` | `AskBuiAiCommand` | リボンの「AIに聞く」。二重に開かない |
| `Bui.Addin` | `RibbonService` | ボタンを1つ追加 |

**選択中の情報に新しい配線は作らない。**
`SelectionTracker` が既にパネルのViewModelへ選択を流しているので、チャットはそこから読む。

チャットウィンドウがパネルのViewModelへ届くよう、`BuiApplication` が起動時に作る
`BuiPaneProvider.ViewModel` を保持する小さな入れ物（`BuiSession`）を置く。
`OnShutdown` で必ず空にする。

## 5. 画面

```
┌─ BUI AIチャット ─────────────────────────────┐
│ データ元 : CSVフォルダ: C:\BUI_PoCData             │
│ 選択中   : 壁 / 基本の壁 LGS65+PB12.5              │
│            仕上 BD-YOSHINO-01 ／ 下地① LGS-KIRII-45│
│ ────────────────────────────────────────────── │
│ あなた: この壁の仕上を不燃にしたい                  │
│                                                     │
│ AI: 今の仕上 BD-YOSHINO-01 は準不燃です。           │
│     同じ厚さで不燃のものが2件あります。             │
│     ・BD-YOSHINO-11 吉野石膏 12.5mm 不燃            │
│     ・BD-CHIYODA-05 チヨダウーテ 12.5mm 不燃        │
│                                                     │
│     絞り込み: 建材分類=せっこうボード ／            │
│               厚さ=12.5 ／ 語=不燃  → 2件           │
│     ［この条件を検索タブへ送る］                    │
│ ────────────────────────────────────────────── │
│ ［質問を入力…                          ］［送信］  │
│ ［会話をリセット］            状態: 応答を待っています │
└─────────────────────────────────────────────────┘
```

**上の2行は常に出す。**どのデータ元で、どの部材について答えているのかが
分からないまま会話が進むのが、この機能でいちばん危ない状態である。

**回答には必ず「絞り込み: … → N件」を添える。**
AIが何をしたのかが見えないと、答えが妥当かを人が判断できない。

**Revitのメインウィンドウを親にした非モーダルウィンドウ**にする。
Revitを操作しながら使え、裏に回り込んで見失うこともない。
「AIに聞く」を二度押しても、同じウィンドウを前面に出すだけである。

**ウィンドウを閉じても会話は残る。**再度開くと続きから使えるが、
**選択中の情報は開くたびに読み直す**（古い部材について答え続けないため）。

送信中は送信ボタンを押せなくし、状態欄に出す。中断ボタンを出す。

### 5.1 「検索タブへ送る」

候補の一覧ではなく、**使った絞り込み条件**を送る。
タブ側の項目が実際にその値へ切り替わり、同じ条件で引き直される。
**AIが何で絞ったかが画面に残る**ので、結果を疑ったときに人が同じ操作を再現できる。

### 5.2 LLMが無効なとき

入力欄はグレーアウトして残す（隠さない）。空欄の下にこう出す。

> LLMが無効になっています。【設定】タブで「LLMを使用する」を有効にし、
> 接続URLとモデルを設定してから「接続確認・モデル一覧取得」を押してください。

グレーアウトを選んだ理由: 入力欄ごと消すと、利用者には「AIチャットが壊れている」ように見える。
グレーのまま理由と対処を出す方が、機能自体は存在することが分かる。

なお、この会話画面のLLM有効・無効の判定は、【設定】タブのチェックボックス（生きた値）ではなく、
**Revit起動時に固定した値**を使う（検索タブの要約と同じ扱い）。会話画面のtranslator/assistantも
起動時固定の接続先・モデルで動くため、判定だけ生きた値にすると「チェックを入れた直後は
入力欄が使えるように見えるのに、実際にはまだ古い設定で動く」というずれが生まれるためである。
設定タブでチェックを変えた後は、次のように再起動が必要な旨を添える。

> 設定を変更した場合、反映にはRevitの再起動が必要です。

## 6. 安全とデータの扱い

LLMへ送るもの。

| 送るもの | 上限 |
| --- | --- |
| 質問文 | そのまま |
| 選択中の1要素の情報 | カテゴリ・タイプ名・層構成・各層のProduct_ID |
| 候補 | **20件まで** |
| 候補1件あたりの属性 | 20個・1つ500文字まで、プロンプト全体16,000文字まで |

上限は既存の `LlmSearchAssistant` と同じ値を使う。2か所で違う上限を持つと、
片方だけ直したときに送信量の想定が崩れる。

送らないもの。マスタ全体、接続文字列、ファイルパス、選択していない要素。

**候補データは「命令」ではなく「信頼できない参照情報」として扱わせる。**
CSVやDBの文章に「〜しろ」と書いてあっても従わない。
既存の `LlmSearchAssistant` のシステムプロンプトと同じ方針である。

**チャットからRevitやCSVへ書く経路は作らない。**
①の出力は絞り込み条件にしかならず、②の出力はテキストにしかならない。
「検索タブへ送る」もタブの絞り込み項目を設定するだけである。

**接続先は既存の `LocalEndpointPolicy` のまま。**ローカル・社内LANのみ。
新しい通信経路は増やさない。

## 7. 異常時の扱い

| 状況 | 動作 |
| --- | --- |
| LLMがOFF | 入力欄はグレーアウトのまま残し、理由と設定タブへの案内を出す |
| 接続できない | 理由をそのまま会話に出す |
| ①のJSONが壊れている | 質問文をキーワード検索に落とし、**そうしたことを画面に出す** |
| ①の条件が全部無効 | 同上 |
| ①・②が中断された | キーワード検索へは落とさず、そのまま「中断しました。」で終える |
| データ元に接続できていない | 「条件に合う製品が無い」とは区別し、理由と設定タブでの確認を案内する |
| 候補0件（データ元は正常） | 「条件に合う製品がありませんでした」＋**使った条件**＋緩める提案 |
| 想定外の例外 | 会話にその旨のAI発言を残し、StatusMessageを更新する（画面を固まらせない） |
| ②が失敗 | 候補一覧を決定的な日本語で出す（AIの説明だけ落ちる） |
| 応答が長い | 設定のタイムアウトを使い、中断ボタンを出す |
| データ元が読めない | データ元の状態をそのまま出す |

## 8. 検証

`Bui.Shared` に入る部分は単体テストで確認できる。

1. ①の出力を条件へ翻訳（正常／壊れたJSON／存在しない値／存在しない列）
2. 値の寄せ（`12.5mm` → 実データの `12.5`）
3. 条件が全部落ちたらキーワード検索へ切り替わること
4. 0件のときの文言に、使った条件が含まれること
5. ②が失敗しても候補一覧が出ること
6. 回答中の存在しないIDに印が付くこと
7. 送信中に二重送信できないこと
8. LLM無効時に入力欄を出さないこと
9. 「検索タブへ送る」が絞り込み条件をパネルのViewModelへ渡すこと
10. 会話をリセットしても選択中の情報は読み直されること

**Revitまたは実LLMが必要で、こちらでは確認できないもの**（会社PCでの確認事項）。

- 別ウィンドウがRevitの前面に出て、裏へ回り込まないこと
- **①のJSONが、利用者のローカルモデルで安定して返ること**
- 応答にかかる時間

最後の点が実務上いちばんの不確定要素である。**小さいモデルはJSONを安定して吐かない。**
外したときは§7のとおりキーワード検索へ落ちるので使えなくはならないが、
「AIが賢くない」と感じる原因はほぼモデル選びになる。
段階12でモデルを変えて試せる手順を用意する。

## 9. 対象外

- チャットからのRevit書き込み、CSV書き込み
- LLMにSQLを書かせる経路
- 会話履歴のファイル保存
- 複数要素をまとめて相談すること（選択中の1要素のみ）
- 画像の受け渡し
