# AIチャットの検索条件をBUIが組み立てる — 設計

日付: 2026-09-10
対象: BUI Revit 2025アドイン（`BUI_Addin_CSharpアドイン`）
前提: `docs/superpowers/specs/2026-09-08-ai-chat-window-design.md`、`docs/superpowers/specs/2026-09-09-ai-chat-conversation-design.md`

## 1. 何を直すか

利用者の報告。

> 『不燃のボードを教えて』などに全く反応してくれない。
> 『ボード』『不燃』といった単語でしか反応せず、
> 複数条件からの検索・提案・比較・簡易計算が出来ない。

### 1.1 確定した原因

会社PCの画面に出ていた文言が決め手になった。

| 画面 | 内容 |
| --- | --- |
| 絞り込み | 0件 |
| 状態 | 条件を組み立てられなかったため、質問文のキーワードで検索しました。 |

**「使えなかった条件: …」が出ていない。**これは `CandidateQueryPlanner.Plan` の
`selections.Count == 0 && text.Length == 0` の道だけを通り、
落とした条件が1つも無いことを意味する。つまり**①のLLMは値を間違えたのではなく、
条件を1つも返していない**（空のJSONか、解析できない応答）。

そのあと2つの欠陥が噛み合う。

1. `CandidateQueryPlanner` は条件が空のとき**質問文をそのまま検索語にする**
2. `ProductCandidateFilter.ContainsText` は `value.Contains(text)` を1回だけ実行する
   （**文章全体を1つの部分文字列として**照合する）

結果、「不燃のボードを教えて」という文字列を含む製品を探すことになり、必ず0件になる。
「ボード」「不燃」が通るのは、それが実データに存在する部分文字列だからである。

### 1.2 設計上の問題

この案件は最初から「**検索は決定的に行い、LLMは説明だけ**」という方針だった
（2026-09-08設計 §2）。AIチャットだけが**検索条件の組み立てをLLMに依存させて**いる。
だからモデルを替えると挙動が変わり、小さいモデルでは何も出ない。方針へ戻す。

### 1.3 確認済みの決定事項

| 論点 | 決定 |
| --- | --- |
| 条件の組み立て | **BUIが決定的に行う。**LLMは上乗せに格下げ |
| 表記ゆれ | **利用者が育てるCSV**で持つ。辞書をコードへ埋め込まない |
| 複数語の照合 | **AND**（すべての語が当たる製品だけ） |
| 会話の表示 | 質問は右詰め・薄いブルー、回答は左詰め |

## 2. 3層で条件を組み立てる

```
質問「PBで不燃のものある？」
      ↓
第1層  マスタの値と直接照合（かな・全半角の揺れを吸収）
        → 「不燃」＝防火性能の値に実在 → 条件
      ↓
第2層  表記ゆれ.csv
        → 「PB」＝建材分類「せっこうボード」 → 条件
      ↓
第3層  LLMに言い換えを挙げさせ、BUIがマスタと突き合わせて採否を決める
        → 1・2が埋めていない項目にだけ足せる
      ↓
      条件＋語 → ICandidateSource（検索タブと同じエンジン）
```

**第1層と第2層だけで、LLMが無くても「PB」「不燃」が通る。**第3層はその上乗せである。

### 2.1 第1層 直接照合

質問文と、**その時点で実際に選べる値**（`CandidateView.Filters`）を突き合わせる。

照合の前に、両方へ同じ正規化をかける。**機械的に導ける揺れだけ**を吸収する。

| 揺れ | 例 |
| --- | --- |
| 全角英数記号 → 半角 | `ＰＢ` → `PB`、`１２.５` → `12.5` |
| カタカナ → ひらがな | `セッコウ` → `せっこう`、`ボード` → `ぼーど` |
| 大文字 → 小文字 | `PB` → `pb` |
| 空白を除去 | `せっこう ボード` → `せっこうぼーど` |

**辞書は使わない。**ここで解けない揺れは第2層の仕事である。

判定は「正規化した質問が、正規化した値を**含む**か」。
同じ項目に複数当たったら**いちばん長い値**を採る。
「せっこうボード」と「ボード」が両方当たるなら前者。短い方を採ると絞り込みが緩くなる。

### 2.2 第1層 検索語の抽出

値そのものは上で拾えるが、「ボード」のような**値の一部**は条件にならない。
これを検索語として拾う。

条件として採った値は、正規化した質問から取り除く。取り除きは正規化後の文字列に対して行う
（正規化で長さが変わるため、元の文字列の位置は使えない）。
残った文字列から、**長さ2以上・12文字以下**の連続部分文字列で、
**いずれかの値に含まれるもの**を集め、他の採用語に含まれるものを捨てて極大なものだけ残す。

「不燃のボードを教えて」から「不燃」を条件として抜いた残りは「のボードを教えて」。
ここから「ボード」が「せっこうボード」に含まれる語として拾える。
「を教えて」はどの値にも現れないので自然に落ちる。

**照合対象は絞り込み項目の値だけに限る。**製品の全属性まで広げると、
備考欄などに現れる短い文字列が語として拾われ、AND検索を無意味に狭める。

上限12文字は暴走防止である。質問が長くても候補語の数は質問長に比例する範囲に収まる。

### 2.3 第2層 表記ゆれ.csv

利用者が育てる1枚のCSV。マスタCSVと同じフォルダに置く。
**SQL接続中もこのファイルを使う**（構成CSVと同じ扱い。2026-09-08 SQL設計 §3.3の先例）。

```csv
言い方,項目,値
PB,建材分類,せっこうボード
石膏ボード,建材分類,せっこうボード
プラスターボード,建材分類,せっこうボード
GB,建材分類,せっこうボード
```

- 「言い方」を正規化して、質問に含まれるかを見る
- 当たったら「項目＝値」を条件にする
- **「値」がマスタに実在するかを必ず確かめる。**無ければその行を落とし、画面へ出す
  （マスタが変わって値が消えたとき、黙って効かなくなるのを防ぐ）
- 「項目」を空にした行は、値を**検索語**として足す（項目を特定できない言い換え用）

**当たらなかった言葉を画面へ出す。**これがこの層の要点である。

> 「PB」は分かりませんでした。表記ゆれ.csv に追加すると、次回から使えます。

追加にRevitの再起動もビルドも要らない。使うほど精度が上がる。

ファイルが無い・読めない場合は**第2層を飛ばして続行する**。
チャットが使えなくなる方が損失が大きい。読めなかったことは画面に出す。

### 2.4 第3層 LLMは言い換えの提案だけ

**①の役割を変える。**いまは「絞り込み項目と値の一覧を見てJSONで条件を組み立てろ」と
要求している。値の一覧は長く、小さいモデルには重い。実際に条件を1つも返していない。

これを**「質問に出てくる建材の言い方を、短い単語で挙げよ」**に変える。

```json
{"intent":"search","terms":["せっこうボード","不燃"]}
```

- `intent` は残す。挨拶を検索へ落とさないために要る（2026-09-09設計）
- `selections` は**廃止**する。項目名を当てさせるのをやめる
- 返った語は**第1層と同じ照合器**に通す。マスタに実在する値・語だけ採用する
- **項目名はLLMに決めさせない。**照合器が語からマスタの項目と値を突き止める。
  「せっこうボード」という語が返れば、それが建材分類の値だとBUIが判定する
- **LLMがマスタに無い製品を作ることはできない。**採否の判断はBUI側にある

プロンプトから項目の値一覧を外せるので、①のプロンプトは大幅に短くなる。

**これは仮説を含む。**「短い単語の列挙なら小さいモデルでも返せる」——外す可能性はあるが、
外しても第1層・第2層で動くため、いまより悪くなることはない。

### 2.5 3層の合成規則

1. **第1層の条件が最優先。**質問文に実際に書かれている値は上書きさせない
2. 第2層は、第1層が埋めていない項目にだけ入れる
3. 第3層は、第1層・第2層が埋めていない項目にだけ入れる
4. 検索語は3層すべてから集める。ただし**条件として採用した値は語から除く**（二重に絞らない）

上位の層ほど確からしい。この順序が、モデルを替えても結果が動かない根拠である。

## 3. 複数語のAND検索

`ProductCandidateFilter.ContainsText` を、**空白区切りの語すべてが当たること**に変える。

```
いま  : どれかの項目が「不燃 ボード」という文字列を含む     → 0件
これから: どれかの項目が「不燃」を含み、かつ
          どれかの項目が「ボード」を含む                    → 該当
```

語ごとに「どの項目でもよい」。項目をまたいで当たってよい
（建材分類に「ボード」、防火性能に「不燃」）。

BUIが質問から抽出した語も、**半角空白で連結して同じ `Text` へ渡す**。
語の受け渡しに新しい経路を作らない。作ると【検索】タブと挙動が食い違う。

**1語だけのときの挙動は変わらない。**【検索】タブの手入力にもそのまま効き、
「不燃 ボード」と打てば絞り込める。

比較は第1層と同じ正規化を通す。「セッコウ」と打っても「せっこう」に当たる。

## 4. 何も拾えなかったとき

いまは文章を検索して0件になり、利用者には何が起きたか分からない。

> 質問から絞り込みに使える言葉が見つかりませんでした。
> 例えば次のように聞いてください。
> 　建材分類: せっこうボード / 防火性能: 不燃 / 厚さ: 12.5
> 「PB」のような言い方は、表記ゆれ.csv に追加すると使えるようになります。

**選べる項目とその値の例を、実データから出す。**固定の例文を書くと、
データが変わったときに存在しない値を案内してしまう。

## 5. 画面に出すもの

拾った条件と語を「絞り込み:」の行にそのまま出す。既存方針どおり、
**AIが何で絞ったかが見えないと結果を信用できない**ためである。

> 絞り込み: 建材分類=せっこうボード ／ 防火性能=不燃  → 12件

どの層が拾ったかは画面に出さない。利用者には関係がなく、行が長くなるだけである。

**「使えなかった言葉」の一覧は出さない。**
出すには、拾えなかった残りの文字列を語へ切り分ける必要がある。
それができないことがこの設計の出発点であり（日本語に語の区切りが無い）、
「のを教えて」のような切れ端を「使えなかった言葉」として並べても直しようがない。

代わりに、**何も拾えなかったとき**（§4）にだけ、選べる項目の例と
表記ゆれ.csv への追加を案内する。拾えた条件が1つでもあれば、
残りについては何も言わない。

**表記ゆれ.csvの行がマスタと合わなかった理由は必ず出す**（§2.3）。
これは利用者が直せる、具体的な問題だからである。

## 6. 会話の左右振り分け

| 発言 | 配置 | 背景 |
| --- | --- | --- |
| あなたの質問 | 右詰め | 薄いブルー（`#FFE3F2FD`） |
| AIの回答 | 左詰め | 既定（背景なし） |

`ChatMessageViewModel` に `IsFromUser` を足し、XAMLはそれで配置と背景を切り替える。
**判定は `Bui.Shared` の真偽値として単体テストで固定する。**
`Bui.Addin` はこちらで検証できないため、判定をXAMLの文字列比較に埋めない。

吹き出しの幅は画面の8割までとする。全幅だと左右に寄せた意味がなくなる。

## 7. 異常時の扱い

| 状況 | 動作 |
| --- | --- |
| 表記ゆれ.csvが無い | 第2層を飛ばして続行。画面には出さない（未設定は異常ではない） |
| 表記ゆれ.csvが読めない・列が違う | 第2層を飛ばして続行。**理由を画面へ出す** |
| 表記ゆれの値がマスタに無い | その行だけ落とし、**どの行かを画面へ出す** |
| LLMが語を返せない | 第1層・第2層の結果で検索する。知らせは出さない（正常な劣化） |
| LLMが返した語がマスタに無い | 黙って捨てる。利用者の言葉ではないため |
| 質問から何も拾えない | §4の案内を出す。全件は出さない |
| 質問が極端に長い | 語の抽出は先頭200文字までを見る |

## 8. 検証

`Bui.Shared` に入る部分は単体テストで確認できる。

1. 正規化（全角→半角、カタカナ→ひらがな、大文字→小文字、空白除去）
2. 「不燃のボードを教えて」から 防火性能=不燃 と 語「ボード」が出ること
3. 同じ項目に複数当たったら長い値を採ること（「ボード」より「せっこうボード」）
4. 表記ゆれ.csvの「PB」から 建材分類=せっこうボード が出ること
5. 表記ゆれの値がマスタに無い行が落ち、その旨が結果に残ること
6. 第1層が埋めた項目を第2層・第3層が上書きしないこと
7. LLMが返した語のうち、マスタに実在するものだけ採用されること
8. 条件として採った値が検索語に二重に入らないこと
9. AND検索（「不燃 ボード」で両方に当たる製品だけ返る）
10. 1語のときの挙動が変わらないこと
11. 何も拾えないときに、実データから作った例が案内に含まれること
12. `IsFromUser` が質問でtrue、回答でfalseになること

**実LLM・Revitが必要で、こちらでは確認できないもの**（会社PCでの確認事項）。

- 利用者のモデルが `terms` を返すこと（返さなくても第1層・第2層で動く）
- 吹き出しが左右に分かれ、質問の背景が薄いブルーになること

## 9. 対象外

- 形態素解析器の導入（辞書とライセンスを持ち込まない）
- 表記ゆれの自動学習（利用者が明示的に追加する）
- 同義語のマスタDB化（まずCSVで運用し、必要になってから考える）
- 【検索】タブの厚さ選択肢の桁（別途。2026-09-10パネル設計 §7）
