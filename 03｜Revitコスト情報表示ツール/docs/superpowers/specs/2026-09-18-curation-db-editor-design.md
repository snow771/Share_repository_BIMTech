# Bui.Curation DB内容更新機能 設計

## 背景・目的

`Bui.Curation`は仮登録データをSQL Server（GoldStandardDB）へ登録する一方向の流れ（仮登録→レビュー→登録）のみを持ち、登録後にDBの内容を修正・削除する手段が無い。

商品のマイナーチェンジによる情報更新、誤登録・テストデータの削除など、登録後にDBの内容を直接直す必要が実運用上発生する。本設計は、`Bui.Curation`へ「登録済みSQL Serverデータを画面上で修正・削除する」機能を追加する。

あわせて、画面上部の接続設定（サーバー名・データベース名・旧新ID CSVのパス）を、起動のたびに手入力し直す不便さも解消する。

## スコープ

- 対象: GoldStandardスキーマの全11表（既存の10表＋今回新たに対応する`Status_Master`）について、既存行の修正・削除
- 対象: 表と表の関連（外部キー）を可視化し、編集・削除前に関連する他表の状況を確認できるようにする
- 対象: 接続設定（サーバー名・データベース名・旧新ID CSVのパス）を次回起動時に自動復元する
- 対象外: 新規行の追加（INSERT）。新規登録は既存の仮登録フロー（Bui.Curationの取込〜登録、またはBUI本体の新規登録機能）が担う
- 対象外: 複数管理者による同時編集の排他制御（既存のBui.Curation全体の前提を踏襲し、利用者1名を想定）
- 対象外: 元のCSVファイルへの反映。この機能はSQL Serverのみを対象とする（CSVは各現場のBUIがローカルに持つ作業コピーであり、この管理者ツールが書き換える対象ではない）

## アーキテクチャ

`Bui.Curation`の`MainWindow`に、既存の「仮登録レビュー」画面とは別に「DB内容更新」タブを新設する（TabControlで両画面を切り替える形にする）。

このタブは、これまでの「CSVフォルダを取込んでSQL Serverへ登録する」という一方向の流れとは別の、「SQL Serverの内容を直接読み書きする」新しい経路を持つ。具体的には:

1. 表選択（ドロップダウン、全11表）
2. 選択した表の全行をSQL Serverから読み込み、Excelライクな`DataGrid`へ表示
3. セルを直接編集、行を選んで削除（複数箇所を自由に編集・削除可能）
4. 「保存」ボタンを押すと、変更内容一覧（表・行・列・旧値→新値、削除予定行）を確認ダイアログで表示
5. 確認ダイアログで内容を確認し、確定すると1トランザクションでまとめてUPDATE/DELETEを実行
6. 実行後、グリッドを再読込して最新状態を表示

行を選択すると、画面内に「関連表パネル」を表示する（下記「表と関連の定義」参照）。

主キー列（例: Products表のproduct_id）はグリッド上で読み取り専用とする。IDを変更したい場合は、削除して仮登録フローから登録し直す運用とする（主キーを直接書き換えると、他表からの外部キー参照が孤立する危険があるため）。

## 表と関連の定義

GoldStandardの全11表について、主キーと「このIDを参照している子表」を以下のとおり定義する。この定義はBui.Shared側の静的なデータとして持ち、テストで固定する。

| 表 | 主キー | 子表（このIDを参照している表） |
|---|---|---|
| Manufacturers | manufacturer_id | Products, Sources |
| Status_Master | status_id | Material_Categories, Sources, Products, Product_Variants, Spec_Master, Product_Specs |
| Reliability_Ranks | reliability_rank_id | Sources, Product_Specs |
| Material_Categories | material_category_id | Products（自分自身:parent_category_idも含む） |
| Sources | source_id | Products(primary_source_id), Product_Specs, Product_Images |
| Products | product_id | Product_Variants, Product_Specs, Product_Images |
| Product_Variants | variant_id | Product_Specs, Product_Images |
| Display_Groups | display_group_id | Spec_Master |
| Spec_Master | spec_key | Product_Specs |
| Product_Specs | gold_id | （他表から参照されない） |
| Product_Images | image_id | （他表から参照されない） |

`Status_Master`は現在の`GoldStandardTables`（Bui.Shared側の表定義）に含まれていないため、今回新たに表名・列定義を追加する（列: status_id, status_group, status_code, status_name_ja, status_name_en, description, display_order, origin）。

## UI: 関連表パネル（フォーカス型）

ブラウザモックアップで「全体ER図タイプ」と「フォーカス型」を比較検討し、フォーカス型を採用した。

選択中の表を中心に、直接関係する表だけを左右に配置する:

- **左側（親表）**: 選択行が参照している表。IDが実在するかどうかの確認用（実在しなければ警告表示。既存の`RelatedTableChecker`と同じ考え方）
- **中央**: 選択中の表・行
- **右側（子表）**: 選択行のIDを参照している表。件数をその場でSQL照会して表示する（例: 「Product_Specs: 5件」）。この件数は、削除前に「この行を消すと5件の関連データが参照切れになる」と気づくための情報表示であり、操作をブロックしない

表を切り替える・行を選び直すたびに、パネルの内容を組み替える。全11表を一度に表示する全体ER図ではなく、常に選択中の表を中心とした一部分だけを表示するため、Status_Masterのように多くの表から参照される表があっても線が交差しない。

## データフロー

1. 「DB内容更新」タブを開くと、表選択ドロップダウンが表示される（初期状態はグリッド空）
2. 表を選ぶと、SQL Serverへ接続し`SELECT * FROM <表名>`で全行を取得、DataGridへ表示する
3. 行を選択すると、関連表パネルがその行のキーにもとづいて件数照会を行い、表示を更新する
4. セルを編集・行を削除マークする（主キー列は編集不可）。この間、変更内容はメモリ上でのみ保持し、SQL Serverへはまだ反映しない
5. 「保存」ボタンを押すと、変更点（更新セル・削除行）を一覧化し、削除予定行については子表の参照件数を再確認して警告文を添える
6. 確認ダイアログで内容を確認し「実行」を押すと、1トランザクションでUPDATE文・DELETE文をまとめて実行する
7. 成功したら該当表を再読込し、グリッドを最新化する。失敗したら理由を表示し、グリッドの内容（未保存の編集）は保持する（再試行できるようにする）

## 接続設定の自動復元

- 「DB内容更新」に限らず、既存の「仮登録レビュー」画面も含め、画面上部のサーバー名・データベース名・旧新ID CSVのパスの3つの入力値を、アプリ終了時（またはウィンドウを閉じる時）に`%LOCALAPPDATA%\StartsCAM\BUI\Curation\ui_settings.json`へ保存する
- 起動時にこのファイルが存在すれば読み込み、3つのテキストボックスへ復元する。存在しなければ、これまでどおりの既定値（サーバー名は`localhost\sqlexpress`、データベース名は`GoldStandardDB`、旧新ID CSVのパスは空欄）を使う

## エラー処理

- **削除予定行に子表からの参照が残っている場合**: 保存確認ダイアログの時点で、削除予定の各行について子表の件数を再確認し、0件でなければ警告文（例:「この行はProduct_Specsから5件参照されています。削除すると参照エラーになる可能性があります」）をダイアログ内に表示する。ブロックはせず、最終判断は操作者に委ねる
- **SQL Server側でエラーが発生した場合（外部キー制約違反等）**: 1トランザクションでまとめて実行するため、1件でも失敗すれば全体をロールバックし、理由をそのまま画面に表示する。中途半端に一部だけ反映された状態を作らない
- **複数管理者による同時編集**: 排他制御は行わない（既存のBui.Curation全体の前提を踏襲）。保存直前に対象行が既に他の操作で変更・削除されていた場合は、SQL側のエラーとしてそのまま表示する

## テスト

- 表と関連の定義（11表のPK・子表マッピング）は、Bui.Shared側の静的なデータとしてBui.Testsで検証する
- 確認ダイアログに出す「変更一覧」の組み立てロジック（旧値→新値の差分抽出、削除予定行への警告文の組み立て）は、SQL接続を持たない純粋関数としてBui.Shared側に切り出し、テスト可能にする
- 実際のSQL読み書き（SELECT/UPDATE/DELETE実行、関連件数の照会）は、これまでの`CurationDbWriter`と同じくBui.Curation側でSqlClientを直接使うクラスに閉じ込め、単体テストはせず目視確認のみとする（会社PCでの確認が必要）
- 接続設定の自動保存・復元（JSON読み書き）は、Bui.Shared側の純粋なロジックとしてテスト可能にする
- 画面（DataGridでの編集、確認ダイアログ、関連表パネル）は既存の方針どおり目視確認のみとする

## 実装しない項目（YAGNI）

- 新規行の追加（INSERT）
- 複数管理者による同時編集の排他制御
- 元のCSVファイルへの反映（この機能はSQL Serverのみを対象とする）
- 主キー列の直接編集（削除して登録し直す運用とする）
